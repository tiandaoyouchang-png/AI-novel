# Artifact Contracts

## Authority order

1. Accepted chapter prose and explicit author decisions.
2. Accepted topic decision, planning Markdown, and continuity YAML.
3. Chapter contracts and context packages.
4. Market scans, candidate slates, reviews, quality debt, indexes, and reports.
5. Conversation previews.

Lower layers must not silently override higher layers.

## Book artifacts

### Discovery

`discovery/market-scan.yaml` stores dated, attributable demand signals. It informs selection but does not become canon.

`discovery/topic-candidates.yaml` compares three to eight original, serially sustainable topics against the same market, reader, and channel.

`discovery/topic-decision.yaml` records the selected candidate, rejected alternatives, accepted trade-off, reader-test hypothesis, and protected-originality rules.

`discovery/hook-experiments.yaml` compares two or three anonymous opening samples for the selected topic. It stores the hook hypothesis, target emotion, reader question, blind-test protocol, observable signals, selected hook, and a reason for rejecting every alternative. An untested author choice must not be described as real reader evidence.

`discovery/topic-selection-report.json` is generated by `novelctl topics`. Do not edit it manually. Its source fingerprints are part of the accepted brief fingerprint, so changed discovery evidence requires regeneration, invalidation, and brief re-approval.

### `author-intent.md`

Record the durable creative intent, desired reader experience, protected themes, and explicit no-go decisions.

### `planning/market-position.yaml`

Define the target platform (`fanqie` or `zhihu-salt`), work form (`long-serial` or `short-complete`), narrow target reader, distribution channel, publication format, repeatable reader promise, acceptable section/chapter-length range, testable commercial assumptions, and content boundaries.

This file, `novel-brief.md`, and the discovery artifacts form one accepted brief fingerprint. The selected candidate's platform, form, target reader, and channel must match this file exactly. A chapter contract must stay inside the accepted length range. Do not hide a positioning change inside an individual chapter contract.

### `current-focus.md`

Record the temporary focus for the next one to three chapters. Keep it replaceable; do not turn it into permanent canon.

### `planning/novel-brief.md`

Before approval, include:

- target reader and publication format;
- primary reader promise;
- protagonist desire and repeatable action loop;
- core conflict and escalation source;
- early hook;
- high-level ending direction;
- protected decisions and open questions.

### Foundation

`story-bible.md` defines the story engine and long-range promises.

`world-rules.yaml` stores stable rule IDs, constraints, costs, and forbidden crossings.

`characters/character-roster.md` indexes active characters. Put every recurring character in a schema-v1 `characters/<character-id>.yaml` profile with stable ID, name, role, core motivation, moral boundary, decision pattern, voice rules, OOC risks, and relationship-specific voice differences. Read only participating profiles per chapter. Keep changing life, injury, location, goal, and knowledge state in `continuity/characters.yaml`, not the stable profile.

`style-profile.yaml` defines abstract POV, tense, pacing, dialogue density, sentence rhythm, description preferences, banned patterns, and scene-type guidance. It must describe craft constraints rather than imitate a named author.

`style-examples.yaml` is an optional library of scene-tagged micro-examples. Every entry must declare `user-owned`, `authorized`, or `public-domain` rights and a source. Unlicensed excerpts are invalid.

`story-guardrails.yaml` is a schema-v1 foundation contract. It locks the premise and signature mechanism, maximum scope, hidden-antagonist ceiling, character capability boundaries, investigation and coincidence rules, period/institution/physics rules, supporting-character goals, permanent consequences, and literal narrative shortcuts that the deterministic quality gate can reject. Changing it requires foundation invalidation and re-approval.

`reveal-policy.yaml` is a schema-v1 schedule for material answers. Each stable reveal ID has an earliest, target, and latest chapter, prerequisite evidence IDs, and a planned/delayed/revealed/cancelled status. The context compiler hides protected meanings before the earliest chapter. A continuity commit marks reveal IDs used by the accepted schema-v3 contract as revealed in the same journaled transaction.

### Volume planning

`volumes/current-volume.md` defines the volume promise, escalation ladder, midpoint shift, climax, payoff, and transition into the next volume. Plan the current volume more firmly than distant volumes.

`arc-grid.yaml` connects main plots, subplots, mysteries, relationships, and character arcs across volumes. It is a planning view with stable IDs, promises, dependencies, volume beats, payoff targets, and idle limits. It must never override facts in accepted prose or `continuity/story-cards.yaml`.

For `short-complete`, use this file as the whole-story plan: opening pressure, causal escalation, reversal, ending payoff, and compression decisions.

### Production and release

`publication/serial-plan.yaml` stores the author-confirmed publication frontier, update target, desired buffer, and blocked days. Inventory is derived from continuity-committed chapters; drafts never count as publishable stock.

`publication/metrics.json` contains only metrics explicitly imported by the author. It is local evidence for hypothesis review and cannot silently revise the accepted market position.

Named revisions under `runtime/revisions/` are immutable recovery snapshots with file fingerprints and a difference summary. Restore through `novelctl`; never hand-edit a revision manifest or `novel-state.yaml`.

## Artifact states

- `missing`: no usable artifact exists.
- `draft`: editable and not authoritative.
- `accepted`: approved or delegated; safe as an upstream dependency.
- `stale`: previously usable but invalidated by a changed dependency.

Never infer `accepted` from file existence alone.
Accepted artifacts store a SHA-256 fingerprint in `novel-state.yaml`. Editing an accepted source requires explicit invalidation and downstream re-approval.

## State changes

Use `novelctl` for `novel-state.yaml`. Do not edit state manually.

An invalid transition must leave the authoritative state unchanged. Generated run snapshots and event logs may remain as diagnostic evidence.
